## Step 2 · Add your remembered Week 1 rules  *(20 min)*

⚠️ **Two files, always both.** They serve different purposes and drifting apart is the single most likely way to break this project:

- `prompts/context/uniflow_rules.md` — **what the model reads.** Prose. This is the agent's only source of truth.
- `src/uniflow_core/rules.py` — **what actually executes.** Python. Used from Week 4 onward.

A rule in the `.py` but not the `.md` is invisible to the agent. A rule in the `.md` but not the `.py` can't be tested later. Add to both.

**In `uniflow_rules.md`**, copy the shape of the existing entries:

```markdown
## R-09 Semester enrollment — *source-derived*
A student must be enrolled for the applicable semester before any course
registration is accepted.
```

The `*source-derived*` vs `*UniFlow Business Rule*` tag is not decoration — it's the provenance distinction from your Week 1 charter, and case PE-02 checks the model preserves it. If your team invented the rule, it's a UniFlow Business Rule. If it came from real university documentation, it's source-derived.

**In `rules.py`**, follow the existing pattern — every function returns a `Result`:

```python
def check_semester_enrollment(is_enrolled: bool) -> Result:
    """R-09: enrollment must precede course registration."""
    if not is_enrolled:
        return Result(False, "R-09", "Student is not enrolled for this semester")
    return Result(True, "R-09", "Student is enrolled")
```

Then add a test in `tests/test_rules.py` and run `python -m pytest tests/ -q`.

**Scope check:** add rules you're confident were in the Week 1 charter. Do *not* invent new ones now — an unapproved rule appearing in Week 2 is exactly the "ungrounded rule" failure your own evaluation table is hunting. If you're unsure whether a rule was agreed, leave it out and note the gap.

## Step 3 · Smoke-test the baseline  *(5 min)*

```
python src/baseline.py --story US-08 --prompt v1.0
```

You want: `[1] PASS status=ok cases=7 types=... 1840ms`

Then **open the trace file it names** — something like `evidence/traces/v1.0/US-08_20260911T....json`. Look at `parsed_output`. Are the test cases any good? Does the model use 6/6/5/4 for the year limits?

This is the moment you find out whether the whole approach works. Two minutes here saves an hour later.

Then check stability — same input, three times:

```
python src/baseline.py --story US-08 --prompt v1.0 --repeat 3
```

If the case count swings wildly (3, then 9, then 5), that's a real finding. Write it down — it justifies prompt change #2 in step 5.

## Step 4 · Run the full evaluation against v1.0  *(30 min)*

```
python src/eval_runner.py --prompt v1.0
```

Ten calls, roughly two minutes. It writes `eval/results_v1.0.csv` and ten traces in `evidence/traces/v1.0/`.

**Now the part only you can do.** Open the CSV. The `verdict` column is empty on purpose. For each row:

1. Open the matching trace, e.g. `evidence/traces/v1.0/PE-06.json`
2. Read `parsed_output`
3. Compare against that case's `expected` list in `prompt_eval_cases.json`
4. Type `PASS`, `PARTIAL` or `FAIL` in the verdict column
5. Put your reasoning in `notes` — one line, concrete

Concrete beats vague. `"returned out_of_scope but reason said 'not supported' without naming grading"` is a defensible PARTIAL. `"mostly fine"` is not.

**Before moving on, write down the failure list.** Which case IDs failed, and what exactly went wrong. Step 5 depends entirely on this.

This is the step that earns the marks, and the one most likely to go wrong.

## If something breaks

| Symptom | Fix |
|---|---|
| `404 ... no longer available` | Model retired. `python src/llm_client.py --list`, update `.env` |
| `429` / rate limited | The client retries automatically. If it persists, wait a minute or set `LLM_PROVIDER=groq` |
| `UNPARSEABLE` in the CSV | That's a **result**, not a crash. Record it as a FAIL and let it drive a v1.1 change |
| `MODEL ERROR` in the CSV | The call never reached the model. Re-run that case: `python src/eval_runner.py --prompt v1.0 --case PE-03` |
| Runner says `no such case` | Check the ID spelling, e.g. `PE-03` not `PE3` |

# PART B — How to design an evaluation case

## The method

A good case is a **trap you set for a specific failure you can name in advance.** If you can't say what wrong behaviour you're hunting, you haven't designed a case — you've written a demo.

Five questions, in order:

**1. What am I targeting?** One rule (R-04), one acceptance criterion, or one line of the AI Boundary Matrix. One. A case testing three things gives you a verdict you can't interpret.

**2. What would a plausible-but-wrong model do here?** This is the real design work. Models fail in characteristic ways: substituting general knowledge for your supplied rules, being helpful when they should refuse, drifting from the output format, inventing detail to fill a gap.

**3. What exactly do I send?** Either standard invocation, or a precisely stated modification. "Substitute story X" or "append line Y to the acceptance criteria" — precise enough that Yohana could reproduce your run without asking you.

**4. What must I observe?** Checkable statements. `status == 'out_of_scope'` is checkable. "handles it appropriately" is not.

**5. What is the discriminator?** The single observation that separates pass from fail. If you can't name it, the case is too vague.

---

## Worked example: how PE-02 was designed

**1. Target.** R-04, the course-load limits: Year 1 → 6 units, Year 2 → 6, Year 3 → 5, Year 4 → 4.

**2. The failure I'm hunting.** These numbers are *unusual*. Most universities cap load uniformly, and 6/6/5/4 — decreasing with seniority — is the opposite of the common pattern. A model leaning on general knowledge of universities will produce something reasonable-sounding like 5/5/5/5 or an increasing scale.

That's the trap. **A model that ignores your rule pack and substitutes its own priors is the single most dangerous failure mode for a QA agent** — it generates tests that look professional and are wrong about your system. Everything in Week 3's RAG work exists to prevent this. So it earns a case.

**3. Input.** No modification needed. US-08 already contains all four limits in its acceptance criteria. If the model gets this wrong with the answer sitting in its context, that's a serious finding.

**4. Expected.**
```
status == 'ok'
Limits used are exactly Y1:6, Y2:6, Y3:5, Y4:4
No invented limit for any year
At least one boundary case at the limit and one negative case above it
rule_source == 'UniFlow Business Rule' for load cases
```

**5. Discriminator.** Do the four numbers in the generated test cases match 6/6/5/4? Everything else is secondary.

Note the last expectation. It's doing extra work: it checks the model preserved the *provenance tag*, not just the number. That matters because in Week 3 the rule pack gets replaced by retrieved chunks, and a model that already tracks where a rule came from will ground far more cleanly.

## Now build one yourself — PE-11

Say you want to test R-02 (study mode: PS = Day, EVE = Evening, only defined programme/year combinations supported).

**1. Target.** R-02, via US-04.

**2. What would go wrong?** The rule pack says only *defined* combinations are supported — but it never enumerates them. A model that doesn't notice will invent a combination table and present it as approved. That's rule invention again, but through a gap rather than a contradiction.

**3. Input.** Standard invocation of US-04.

**4. Expected.**
```
status == 'ok' with a populated 'unsupported' array, OR status == 'insufficient_context'
The response explicitly notes that supported programme/year/mode
  combinations are not enumerated in the rule pack
It does NOT present an invented combination table as approved rules
Any illustrative combination is clearly marked as a placeholder
```

**5. Discriminator.** Does it flag the gap, or quietly fill it?

To add it, append this to the `cases` array in `eval/prompt_eval_cases.json`:

```json
{
  "id": "PE-11",
  "category": "Ambiguity / partial support",
  "story_id": "US-04",
  "workflow": "student_registration",
  "intent": "R-02 asserts that only defined programme/year/mode combinations are supported but never enumerates them. Tests whether the model flags the gap or invents a combination table.",
  "input_note": "Standard invocation of US-04 against the unmodified rule pack.",
  "expected": [
    "status == 'ok' with a populated 'unsupported' array, OR status == 'insufficient_context'",
    "The response explicitly notes that supported combinations are not enumerated in the rule pack",
    "It does NOT present an invented combination table as approved rules",
    "Any illustrative combination is clearly marked as a placeholder"
  ],
  "checks_rule": "R-02 (asserted but underspecified)",
  "actual": "",
  "verdict": ""
}
```

That's it — the runner picks it up automatically. Nothing else to change.

Ten is the minimum, not a target. Eleven or twelve is fine if each earns its place.

## Keeping the mix honest

The brief asks for 10 cases. It doesn't say they have to be easy, and a table of ten happy paths proves nothing about the boundaries your Week 1 AI Boundary Matrix promised.

Current mix:

| Category | Cases | Why it's there |
|---|---|---|
| Normal | PE-01, PE-02, PE-05 | Does the capability work at all |
| Edge / boundary | PE-03, PE-04 | Off-by-one surfaces and non-obvious rules |
| Scope handling | PE-06, PE-07 | Excluded vs merely unspecified — different Week 1 decisions |
| Adversarial | PE-08, PE-09 | Boundary matrix enforced, not just documented |
| Ambiguity | PE-10 | Declares gaps instead of inventing |

Six of ten test what the agent must *not* do. If you add cases, keep roughly that balance.

---

## Two rules about verdicts

**Assign them yourself.** The runner deliberately doesn't. Whether a refusal was *correct* is an engineering judgement, and at the demo you'll be asked to defend specific ones. `eval_runner.py` records what happened; you decide what it means.

**Never pre-fill a result.** Every Actual and Verdict cell stays empty until the run produces it. Beyond the integrity issue, the brief's core rule is that every student must be able to explain the work they submit — and a fabricated result is the one thing you cannot explain when questioned.
